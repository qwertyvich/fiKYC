# Оплата на карту · @GatewayReqBot

Покупатель проверяет корзину, принимает предупреждение о 15 минутах, получает карту под сумму заказа и прикрепляет квитанцию. Квитанция сохраняется в SQLite и отправляется менеджеру через платёжного бота. Получение файла не подтверждает поступление денег: администратор проверяет перевод и нажимает «Подтвердить поступление денег» в боте или в панели.

## Подключение

1. В `.env` сервера задайте **GATEWAY_BOT_TOKEN**. Это отдельный токен от **BOT_TOKEN**, которым подписан вход в Mini App. Токен не должен попадать в `VITE_*`, исходники или публичные настройки. Локальный токен уже записан в игнорируемый `.env`.
2. Для **@GatewayReqBot** в **@BotFather** включите **Bot-to-Bot Communication Mode**, отключите **Group Privacy Mode**. Добавьте его участником супергруппы `-1002278926769`. В этой комбинации настроек права администратора не обязательны для получения обычных сообщений от **@feweqw34234_bot**: https://core.telegram.org/bots/features#bot-to-bot-communication . Если изменяете Privacy Mode, проверьте применение настройки в группе; при необходимости добавьте бота заново.
3. **@tcmai** открывает **@GatewayReqBot** и нажимает **Старт**. Telegram не разрешает начать обычную личную переписку с пользователем только по его username. Первое входящее сообщение привязывает получателя к стабильному числовому ID; последующая смена владельца username не перенаправляет квитанции.
4. В панели **Оплаты** проверьте исходный чат, доверенного отправителя и получателя. Вместо username можно задать числовой ID. Для отдельного чата квитанций укажите его ID и добавьте туда бота. Подтверждать оплаты кнопкой в таком чате могут пользователи из `ADMIN_TELEGRAM_IDS`/настроек магазина; в личной переписке — привязанный получатель.
5. Запустите `npm run build` и `npm run server` (локально) или `npm start`/Docker Compose (production). Не запускайте несколько процессов, использующих `getUpdates` одного бота. Если бот использует внешний webhook, сначала согласованно переключите доставку: код не удаляет существующий webhook.
6. Проверьте панель: есть связь с Telegram, получено сообщение доверенного отправителя и карта доступна. Не выполняйте тестовый перевод. Исходная группа используется исключительно для чтения: бот не отправляет туда команды, сообщения, файлы или квитанции. Если ранее не получено ни одного объявления, шлюз молча ждёт его или начальной приватной загрузки владельцем; история группы через Bot API недоступна.

Первоначально выдача включена, но без связи и подтверждённых реквизитов карта не выдаётся: заказ передаётся менеджеру. Отключение выдачи в панели также отзывает уже открытые реквизиты.

Для reverse proxy отключите буферизацию маршрута `/api/payments/*/events` и разрешите долгие SSE-соединения. Backend выставляет `X-Accel-Buffering: no`; для nginx используйте `proxy_buffering off` и достаточный `proxy_read_timeout`. Все API и события должны идти через тот же HTTPS origin, что и Mini App.

## Разобранные сценарии

| Сообщение источника | Поведение |
| --- | --- |
| Одна/несколько карточек с банком, ФИО, картой и лимитами | Полный актуальный список. Отсутствовавшие в новом списке карты отзываются. |
| Повтор прежней карточки | Без дублирования и продления уже выданных 15 минут. |
| Увеличение лимита | Подходящие открытые оплаты остаются действительны. |
| Уменьшение лимита | Отзываются оплаты, которые больше не входят в диапазон. |
| Изменение банка/ФИО | Прежние выданные реквизиты отзываются. |
| Стоп с номером карты | Эта карта исключается, остальные остаются. |
| Стоп с блоком «Актуальные реквизиты» | Остановленная карта исключается, оставшийся блок становится полным актуальным списком. |
| Общий стоп | Отзываются все карты и активные оплаты. |
| Неполное/неоднозначное объявление реквизитов | Выдача приостанавливается до корректного нового объявления. Обычный разговор и команды не меняют карты. |
| Сообщение из другого чата/от другого отправителя | Игнорируется. Доверенный username при первом сообщении закрепляется за ID. |
| Повтор/старое сообщение | Не отменяет более новое состояние; offset сохраняется в SQLite. |
| Перезапуск/потеря связи | Открытые оплаты отзываются. При коротком разрыве последний список карт восстанавливается только после обработки очереди Telegram со стопами; при разрыве 23 часа и более требуется новое объявление. |

Из двух подходящих карт выбирается случайная. Проверяется весь платёж в рублях, включая количество товара. Карты с максимумом 8 000 ₽ не выдаются для заказа 10 000 ₽. Сумма ниже минимума, неподходящая валюта и отсутствие подходящей карты переводят заказ менеджеру; платёж не разбивается. Цены и наличие берутся с сервера, изменение цены относительно проверенной корзины требует обновить корзину. USD не конвертируется автоматически.

## Открытая оплата

- Срок отсчитывается сервером; обновление страницы не продлевает 15 минут. Истечение скрывает номер и показывает «Ожидаем квитанцию».
- Изменения передаются через SSE, контрольный пакет приходит раз в секунду. Ошибка соединения, отсутствие пакетов более 2,5 секунд и скрытие приложения убирают номер до восстановления проверки. Перед копированием выполняется отдельная серверная проверка.
- После стопа прежняя попытка не оживает, даже если та же карта появилась снова. Новая выдача требует действия «Не успел оплатить» и подтверждения, что деньги ещё не переводили. Повторное нажатие возвращает ту же новую попытку.
- Квитанцию можно приложить после истечения срока и после стопа, в том числе к предыдущей попытке. Она останавливает другие активные попытки этого заказа. Подтверждение нескольких квитанций одного заказа списывает остаток один раз.
- Оплаты привязаны к подтверждённому Telegram ID и доступны на других устройствах этого пользователя. Локальный просмотр без Telegram хранит принадлежность по cookie браузера.
- После ручного подтверждения поступления денег заказ получает статус «Оплата подтверждена», остаток уменьшается в одной транзакции. Автоматическая передача цифрового товара и интеграция с банковской выпиской в эту задачу не входят. Остаток до подтверждения не резервируется; при нехватке сервер запрещает подтверждение, вопрос решает менеджер.

**Граница гарантий:** Bot API не сообщает об обычном удалении сообщений группы; источнику необходимо присылать явный стоп или обновлённый список. Также нельзя отменить уже скопированный номер, начатый банковский перевод или устранить задержку между источником, Telegram и устройством. Поэтому интерфейс не обещает безусловную доступность карты на все 15 минут. Если источник не передаёт стопы, интерфейс не может достоверно обнаружить остановку карты. Шлюз не запрашивает список в группе и не пишет в неё. Само по себе отсутствие новых объявлений не отзывает карту, пока связь с Telegram исправна; стопы должны приходить от источника.

## Квитанции и доставка

В приложении: PDF/JPG/PNG/WebP до 12 МБ с проверкой сигнатуры файла, серверной принадлежностью заказа и ограничением частоты. Файл сохраняется в SQLite **до** ответа об успешном приёме, затем отправляется от имени @GatewayReqBot в отдельный чат/лично администратору. Публичных URL файлов нет.

Кнопка «Отправить менеджеру в Telegram» открывает прямой чат с контактом магазина и подставляет номер заказа. Покупатель прикладывает файл в этом чате сам. Вторая возможность — прикрепить квитанцию на сайте; она сохраняется до ответа об успешном приёме и видна в защищённом разделе «Оплаты → Открыть квитанции». Покупателю не показываются имя, ссылки и коды внутреннего шлюзового бота. Шлюз не отправляет покупателю личные уведомления; статус обновляется в Mini App.

Очередь отправки, квитанции, offset, привязки ID и попытки оплаты переживают перезапуск. Сбой Telegram не теряет файл; применяется повтор с увеличивающейся паузой и учётом `retry_after`. Доставка имеет семантику **как минимум один раз**: при обрыве после принятия файла Telegram, но до подтверждения backend, возможно повторное уведомление. Подтверждение оплаты идемпотентно. Число ожидающих отправок видно в панели.

Доступность карты не зависит от подключения получателя квитанций. Если Telegram-доставка менеджеру недоступна, квитанция остаётся в базе и доступна в админке; очередь повторяет доставку. Покупатель общается только с магазином.

База содержит квитанции и реквизиты: резервные копии и доступ к volume должны быть доступны только владельцу сервера. Политика удаления данных должна учитывать работу магазина; автоматическое удаление квитанций пока не включено.

## Развитие и проверки

- `server/gateway/parser.mjs`: распознавание сообщений источника, без исполнения текста.
- `server/gateway/providers.mjs`: реестр провайдеров и выбор подходящих реквизитов.
- `server/gateway/gateway.mjs`: выдача/отзыв, провайдер, заказы и попытки, квитанции, outbox, Telegram worker.
- `src/PaymentFlow.tsx`: покупательский сценарий, контроль доступности и история.
- `src/admin/GatewayPage.tsx`: настройки и подтверждения.

Провайдер выбирает реквизиты через `select(amountMinor)`, заказ хранит `provider`, сумма хранится в копейках. Это точка расширения для следующих способов оплаты. Для агрегатора с внешним созданием платежа понадобятся отдельный адаптер, аутентификация webhook и проверка статуса на его API; текущий Telegram-код не должен становиться обработчиком банковских webhook.

```bash
npm test
npm run test:server
npm run build
npm run test:gateway
```

`server/fixtures/feed-scenarios.json` содержит 42 объявления из предоставленного экспорта за 4–8 ноября 2026 года с заменёнными номерами и именами. Тесты проверяют полный прогон, стопы уже выданных реквизитов, лимиты, недоступность Telegram, принадлежность заказов, просрочку, повторные попытки, файлы, доставку и подтверждение. Браузерный сценарий использует изолированную SQLite в памяти и фиктивный Telegram-транспорт; реальные сообщения не отправляются. Скриншоты: `qa/gateway/`.

## Production на kyc.kraken892.rest

Изолированный Compose-проект **fikus**, сервис **app**, содержит API и worker @GatewayReqBot в одном процессе. Он слушает только `127.0.0.1:8787`. Ограничения: до 384 МБ RAM и 0,5 CPU; сборка frontend выполняется локально. Конфигурация: `deploy/compose.production.yml`; runtime-образ: `deploy/Dockerfile.runtime`.

Релизы находятся в `/opt/fikus-miniapp/releases/<commit>`, активный frontend — симлинк `/opt/fikus-miniapp/current`. Постоянные данные и закрытый `.env` находятся в `/opt/fikus-miniapp/shared/`. `scripts/bootstrap-production.mjs` импортирует только каталог и настройки при первом запуске; существующую production-базу он не перезаписывает. Привязки пользователей, сессии и квитанции из локальной разработки не переносятся.

Nginx изменяется только для `kyc.kraken892.rest`: статические файлы продолжают обслуживаться nginx, `/api/` проксируется в контейнер, разрешены квитанции до 12 МБ и SSE без буферизации. Конфигурации других доменов и их Docker-проекты не меняются. Перед переключением сохраняются конфигурация vhost и путь прежнего релиза. Обновление не требует `docker system prune`, перезапуска Docker или остановки других Compose-проектов.

Исходный чат защищён от любых записывающих Telegram API-вызовов на уровне транспорта. Получателем квитанций нельзя назначить исходную группу. Отложенные задания отправки команд от прежней версии отменяются, а не исполняются.

## Первая загрузка и диагностика источника

Наличие карты в истории группы не означает, что Bot API передал её новому боту. Если объявления ещё не приходили, владелец может в разделе «Начальные реквизиты» приватно загрузить полный актуальный список, подтвердив отсутствие более позднего стопа. Этот список действует максимум 15 минут, срок оплаты ограничен тем же временем; входящие стопы немедленно его отзывают. После первого распознанного сообщения источника начальная загрузка не может перезаписать его состояние. Для серверной настройки есть `scripts/import-requisites.mjs <private-file> --confirmed-current`; скрипт не обращается к Telegram.

Входящие сообщения группы сохраняются в закрытом журнале до 500 записей вместе с решением парсера. Панель показывает время последнего сообщения, доверенного отправителя, ошибки связи и причину отклонения. Полные тексты и номера карт не входят в диагностический ответ API. Контрольные точки обработки очереди переживают перезапуск; объявления с задержкой больше минуты не выбрасываются. Старый стоп не отменяется запоздавшим снимком с более ранней датой.

Если заказ уже перешёл менеджеру, кнопка «Проверить реквизиты» позволяет получить карту после её появления. Покупатель подтверждает, что ещё не переводил деньги. При отсутствии карты новая заявка менеджеру не дублируется.
